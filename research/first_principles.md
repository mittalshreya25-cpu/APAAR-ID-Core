# First Principles — architecture evidence brief

Date/access date: 2026-10-28 (India). Participant, not council chair. No code was supplied or run. The baseline is a conversation export, not evidence that the claimed engine, 37 tests, or throughput exists locally. All recommendations below are proposed decisions, not measured outcomes. Sources are official documentation; documentation versions identify what was inspected, not a demand to use a particular latest release.

## Atomic sourced claims for independent review

### FIRST-1 — RLS does not constrain every database identity or operation

**Fact:** PostgreSQL table owners normally bypass row security; `FORCE ROW LEVEL SECURITY` subjects an owner, but superusers and `BYPASSRLS` roles still bypass it. Whole-table operations and integrity checks have exceptions. RLS policies are permissive/OR by default, so an additional broad policy can widen access. Confidence: high, explicit documented semantics.

**Exact excerpt (14 words):** “Superusers and roles with the `BYPASSRLS` attribute always bypass the row security system”.

**Source:** PostgreSQL Global Development Group, *PostgreSQL 18 Documentation, 5.9 Row Security Policies*, version 18, page date unstated, accessed 2026-10-28. [Source](https://www.postgresql.org/docs/18/ddl-rowsecurity.html). Locators: owner/bypass paragraphs, policy combination paragraph, referential-integrity paragraph; retrieved lines 22–33 and 182.

**Decision:** Separate migration/owner credentials from runtime credentials. Runtime is a non-owner, non-superuser, no `BYPASSRLS`, without membership permitting escalation into an owner role. Enable and force RLS on tenant tables; explicitly test read and write policies. Restrict grants, especially DDL/TRUNCATE. Use tenant-inclusive foreign keys to prevent linking an institution's enrolment to another institution's submission. Normalize constraint errors at the API boundary rather than exposing existence clues. Test through actual runtime credentials, never only as the migration owner.

### FIRST-2 — tenant context must have transaction scope with pooled connections

**Fact:** `SET SESSION` can survive transaction commit, whereas `SET LOCAL` ends with the transaction; outside a transaction it has no effective scope. SQLAlchemy releases a connection to its pool when the session transaction ends. Confidence: high.

**Exact excerpts:** PostgreSQL: “The effects of `SET LOCAL` last only till the end of the current transaction” (16 words). SQLAlchemy: “released to the connection pool” (5 words).

**Sources:** PostgreSQL Global Development Group, *PostgreSQL 18 Documentation, SET*, version 18, page date unstated, [source](https://www.postgresql.org/docs/18/sql-set.html), Description/LOCAL, retrieved lines 28–48. SQLAlchemy authors, *Session Basics*, inspected 2.0 documentation (page identifies 2.0.55, release date 2026-10-16; this is a maintenance documentation series, not a current-version recommendation), [source](https://docs.sqlalchemy.org/en/20/orm/session_basics.html), “What does the Session do?”, retrieved lines 120–121. Both accessed 2026-10-28.

**Decision:** Authenticate first, resolve institution membership server-side, open an explicit transaction, then use parameterized `set_config('app.tenant_id', ..., true)` before any tenant SQL. Never accept an arbitrary client tenant header as authority. The policy must deny rows when context is missing. Reapply context for every new transaction, including a worker job; do not allow helper commits to silently begin a new unscoped transaction. A custom tenant setting is protection against missing filters, not against a compromised application able to execute arbitrary SQL with the same credential. Keep SQL parameterized and privileges narrow.

### FIRST-3 — application count-then-write cannot alone make certification atomic

**Fact:** Read Committed is PostgreSQL's default and successive queries can observe different committed states. Serializable can reject conflicting executions and requires whole-transaction retries. A row locked `FOR UPDATE` prevents other transactions from locking/modifying that same row until transaction end. Confidence: high.

**Exact excerpts:** transaction isolation: “applications using this level must be prepared to retry transactions due to serialization failures” (15 words); explicit locking: “Row-level locks are released at transaction end” (8 words).

**Sources:** PostgreSQL Global Development Group, *PostgreSQL 18 Documentation, 13.2 Transaction Isolation*, version 18, [source](https://www.postgresql.org/docs/18/transaction-iso.html), §§13.2.1/13.2.3, retrieved lines 62–63, 109–110, 135–143; *13.3 Explicit Locking*, [source](https://www.postgresql.org/docs/18/explicit-locking.html), §13.3.2, retrieved lines 94–102 and deadlock ordering advice 141–143. Page dates unstated; accessed 2026-10-28.

**Decision:** Stage uploads without changing accepted enrolments. At certification lock a stable, pre-existing scope row for institution + programme offering + admission year; verify candidate version and approval/rule versions; recompute intake against the effective accepted set; write accepted snapshot pointer, audit event, and durable job/outbox rows in one transaction. Every path changing that effective set must acquire the same scope lock. Multiple-scope operations lock scopes in a fixed order. The lock on a parent row does not automatically protect child rows unless this protocol is enforced. Decide whether each upload replaces a complete scope or is a delta; do not add a replacement file's count to the previous file. An approval update must use the same locking/version protocol. Use Serializable with bounded retries instead if the invariant spans scopes and a reliable lock protocol becomes harder than the retry policy. Do no network calls inside this short transaction.

### FIRST-4 — simultaneous enrolment is not universally invalid

**Fact:** UGC's modified guidelines permit two physical programmes when class timings do not overlap, physical plus ODL/online, or up to two ODL/online programmes, subject to recognized providers and relevant statutory/professional council rules. They exclude Ph.D. The 2025 modification changes historical validity treatment; it does not establish blanket AICTE permission for every programme combination. Confidence: high for UGC wording; applicability to a specific AICTE programme remains unresolved.

**Exact excerpt (12 words):** “class timings for one programme do not overlap with the class timings”.

**Source:** University Grants Commission, *Partial modification of the UGC Guidelines for Pursuing Two Academic Programmes Simultaneously*, letter 2025-06-05; enclosed revised guidelines marked April 2025. [Official PDF](https://www.ugc.gov.in/pdfnews/6493421_UGC-Guidelines-pursuing-two-academic-programmes-simultaneously.pdf). Locators: PDF page 1 modification; PDF pages 4–5, Guidelines 1–5 and concluding exclusions; retrieved lines 113–142. Accessed 2026-10-28. [Official index entry](https://www.ugc.gov.in/Guideline), first row, published 05/06/2025.

**Decision:** One identity may have many temporal enrolments. Do not put a global `UNIQUE(apaar_id)` on enrolments or auto-reject every overlap. Separate exact duplicate submission rows, duplicate institutional enrolment identifiers, historical transfer/withdrawal, and potentially incompatible overlapping programmes. Produce an explainable review case with date intervals, programme mode, and applicable rule version. Restrict other-institution details to a regulator workflow; institution response should disclose only an authorized conflict indicator. Do not assert fraud from an overlap.

### FIRST-5 — response background tasks are in-process; a PostgreSQL job table is an available simpler durable boundary

**Fact:** Starlette documents its background tasks as in-process and attached to a response. PostgreSQL explicitly describes `SKIP LOCKED` as useful for multiple consumers of queue-like tables, while warning its inconsistent view is unsuitable for general work. Confidence: high for mechanics; durability of the proposed job implementation must be tested.

**Exact excerpts:** Starlette: “in-process background tasks” (3 words); PostgreSQL SELECT: “multiple consumers accessing a queue-like table” (7 words).

**Sources:** Starlette, *Background Tasks*, unversioned documentation, page date unstated, [source](https://starlette.dev/background/), introductory paragraphs and Important exception note, retrieved lines 58–60, 124–126; PostgreSQL Global Development Group, *PostgreSQL 18 Documentation, SELECT*, version 18, [source](https://www.postgresql.org/docs/18/sql-select.html), Locking Clause, retrieved line 401. Accessed 2026-10-28.

**Decision:** Start with one API process, one independently restartable Python worker process and PostgreSQL. A committed `jobs` row is the queue; no Redis, Celery, Kafka or workflow platform is required initially. Worker claims a row in a short transaction using `FOR UPDATE SKIP LOCKED`, records a lease/attempt token, commits, processes outside the lock, then completes only if its lease token still matches. Expired leases retry; cap attempts, retain terminal failures, expose retry status. Give each effect an idempotency key/unique constraint. Expect repeated execution after a crash. When sending external webhooks, insert an outbox row in the same business transaction, deliver later, and treat delivery as at-least-once. Do not claim exactly-once external delivery. Use `SKIP LOCKED` for claiming work, never for the intake aggregate.

### FIRST-6 — typed request validation and schema generation do not replace explicit integrity/migration review

**Fact:** Pydantic coerces compatible input values by default; strict mode changes coercion behavior with type/JSON exceptions. PostgreSQL CHECK cannot reliably enforce a condition over other rows. Alembic calls autogeneration candidate migrations requiring manual review and correction. Confidence: high.

**Exact excerpts:** Pydantic: “By default, Pydantic will attempt to coerce values” (9 words); constraints: “does not support `CHECK` constraints that reference table data other than the new or updated row” (18 words); Alembic: “always necessary to manually review and correct the candidate migrations” (11 words).

**Sources:** Pydantic, *Strict Mode*, unversioned latest documentation, page date unstated, [source](https://pydantic.dev/docs/validation/latest/concepts/strict_mode/), Overview, retrieved lines 146–152; PostgreSQL Global Development Group, *PostgreSQL 18 Documentation, 5.5 Constraints*, version 18, [source](https://www.postgresql.org/docs/18/ddl-constraints.html), §5.5.1 Note, retrieved lines 94–101; Alembic, *Auto Generating Migrations*, page identifies documentation 1.20.1, date unstated, [source](https://alembic.sqlalchemy.org/en/latest/autogenerate.html), “What does Autogenerate Detect (and what does it not detect?)”. All accessed 2026-10-28.

**Decision:** Keep APAAR and local student IDs as strings; CSV ingestion has an explicit normalization phase preserving raw values and source row number before strict typed validation. Reject unknown API fields where appropriate. Enforce row-local domain constraints and uniqueness/FKs in PostgreSQL, aggregate rules in certification transactions, and authorization in application plus RLS. Hand-author/review RLS policies, grants and other security DDL in Alembic revisions. A YAML value change is a policy change requiring approval and examples, not automatically a correct official rule.

## Proposed architecture and model (decisions, not external facts)

**Stack:** Python + FastAPI + Pydantic + SQLAlchemy + Alembic + PostgreSQL is sufficient for a solo developer's backend-first system. Prefer synchronous SQLAlchemy initially with ordinary FastAPI `def` endpoints and a separate worker; introduce async database code only for measured needs. One session per request/job; a transaction boundary belongs to the use case, not a repository helper. A modular monolith with `identity_access`, `institutions`, `intake`, `submissions`, `validation`, `review`, `verification`, and `audit` modules supplies boundaries without deployable services. Version-lock dependencies during implementation after confirming compatibility; inspected documentation labels are not a verified package lock.

**Trust boundaries:** (1) uploaded bytes/client input to bounded parser, (2) authenticated principal to authorized institution/role, (3) application transaction to least-privilege/RLS database, (4) tenant-only operations to explicitly authorized regulator cross-tenant detection, (5) accepted record to narrowly scoped verifier disclosure, (6) worker to untrusted external integration. The mock registry must return `MOCK_MATCH`/`MOCK_NO_MATCH`/`MOCK_UNAVAILABLE` provenance and fixture version, never “officially verified”. A student identifier is not a bearer authorization token. Do not require identity documents for the mock demonstration.

**Model:** `institution`; `programme_offering`; `intake_approval` (academic/admission year, approval source, effective interval, version); centrally restricted `student_identity`; tenant `enrolment` (student, offering, local ID, admission cohort, mode, status, valid_from/to); `submission`/immutable `submission_version`; `staged_row`; `validation_run`; `finding`; `review_case`/decision; `accepted_snapshot`; `audit_event`; `job`; and optional webhook `outbox`. Keep upload history separate from the effective accepted record. Make correction a new version linked to superseded data, not an invisible edit. `NRI`, citizenship and OCI are distinct attributes from the actual seat/admission allocation; retain explicit category semantics and source rather than one mutually exclusive mega-enum. Admit unresolved rule/category definitions rather than hard-code guessed arithmetic.

**Reproducibility:** A validation run records immutable input version/content hash, parser/schema version, rule bundle version/hash, evaluator code revision, approval versions, mock registry fixture/result snapshot, evaluation timestamp, and reference-data/accepted-snapshot IDs. Store calculated operands and rule IDs with each finding. Rule bundles use schema-checked parameters/metadata calling allowlisted Python functions, not arbitrary eval expressions. Separate authority status (`verified_primary`, `assumption`, `demo_only`) from severity. Preserve old bundles and findings; a new policy creates a new run. Hashes detect content change only when the original bytes/snapshots remain available. Time-dependent checks receive an explicit evaluation time. Global conflict results state the reference snapshot/watermark: they are not an eternal truth.

**Minimal proof before adding features:** real PostgreSQL tests showing runtime-role tenant denial (including guessed IDs and child foreign keys); reuse one pooled connection across tenant A, tenant B, missing context, and rollback; two simultaneous certifications cannot both validate against stale intake; replaced file is counted once; certification after approval/rule/input change is refused or reevaluated; legitimate concurrent programme/transfer fixtures avoid a fraud verdict; worker crash after side effect causes safe retry; replay of the same pinned run reproduces findings. Benchmark only after this path exists, stating hardware, database, dataset, concurrency, end-to-end latency, memory and constraints enabled. The historical synthetic throughput claim proves none of this.

## Contrary evidence, pitfalls and unresolved questions

- Strongest counterargument to the simple stack: a database queue itself needs lease, retry, idempotency and monitoring code. If measured job volume, scheduling complexity or operator reliability exceeds this small implementation, a maintained durable worker system may be simpler overall. The recommendation is proportional scope, not an anti-Celery rule. FastAPI's own [background-task caveat](https://fastapi.tiangolo.com/tutorial/background-tasks/#caveat) names Celery for heavier/multiprocess work and acknowledges extra configuration.
- RLS does not protect uploaded files, logs, cached results, exports, arbitrary SQL executed by a compromised backend, or external identity systems. Audit each actual disclosure path. “Tamper-evident” in the same database is not protection against a database administrator rewriting both data and chain; treat stronger audit anchoring as a separately justified future requirement.
- A locked intake row only serializes the scopes actually covered. A new direct import, correction, withdrawal, approval amendment or admin script can break the invariant if it bypasses the protocol. Certification is a record-quality decision, not necessarily an admission booking/seat-reservation operation. Retain rejected/over-intake submissions as findings rather than losing their evidence.
- Exact capacity bucket arithmetic, effective approval supersession, treatment of carryovers/lateral entry, which counts are intake versus all-year enrolment, and whether certification blocks particular violations remain domain questions. Refer these to the council's AICTE specialist and verified primary handbook clauses.
- Maker/checker separation, employer consent flows and signed receipts may be sensible product choices, but the baseline does not establish their detailed legal/organizational authorization model. A solo developer can demonstrate two test actors without claiming two-person real operational staffing.
- Weakest load-bearing recommendation: workload sufficiency of a PostgreSQL worker queue. No implementation, workload envelope or operations evidence exists yet. It should change if repeatable tests show unacceptable queue lag, database contention, recovery complexity, or a required supported workflow feature.

## Author response to Film Room's non-author review — 2026-10-28

Accepted the implementation clarifications in `research/review_first_principles.md`; these refine proposed acceptance conditions, not implemented behavior:

- **FIRST-2:** PostgreSQL's [SET documentation](https://www.postgresql.org/docs/18/sql-set.html), Description, also states that rollback to a savepoint preceding the setting cancels it. Establish trusted tenant context at transaction entry; if recovery crosses that setup boundary, abort the use case or deliberately re-establish context from server-trusted state before further tenant SQL. Likewise do not continue assuming a scope lock survived rollback to a savepoint preceding its acquisition. Add a recovery regression test.
- **FIRST-3:** The initial explicit-mutex protocol uses **READ COMMITTED**. Acquire the stable scope-row lock first; only after acquisition, issue the aggregate recount in a **subsequent SQL statement** so its statement snapshot includes changes committed by a transaction that held the lock before this one. Do not reuse a pre-lock validation count, place lock waiting and count into one statement expecting a refreshed snapshot, or silently run this protocol under a fixed earlier snapshot. All imports, replacements, corrections, withdrawals, administrative effective-record changes and approval mutations must follow the same scope protocol, and the lock remains held until certification, snapshot, audit and durable-job writes commit. Domain acceptance rules still determine whether an excess finding blocks certification.
- **Serializable alternative:** use it as a coordinated transaction protocol covering the relevant predicate reads and state-changing transactions, not just an isolation switch on one endpoint. Retry the **entire aborted transaction**, including its reads and computations, with bounded handling for serialization/deadlock failures; do not reuse an aborted result or perform irreversible external effects before commit. The [PostgreSQL isolation documentation](https://www.postgresql.org/docs/18/transaction-iso.html), §§13.2.1/13.2.3, supplies the relevant snapshot/retry semantics. Concurrency tests with separate database connections remain required before claiming safety.

FIRST-4's current caveats remain: the UGC modified guideline is conditional, excludes Ph.D. and does not establish compatibility for every AICTE programme pair or all historical overlaps. FIRST-5's queue sufficiency remains an unmeasured workload decision. The reviewer, not this response, determines whether these clarifications resolve the review.
