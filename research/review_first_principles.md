## Material challenges and resolution

### 1. Scope lock is not an automatic aggregate constraint

**Challenge:** A parent/scope row lock cannot by itself prohibit arbitrary child inserts or changes outside that same lock protocol. A precomputed count, a count in a query whose snapshot precedes lock acquisition, or an unsuitable fixed snapshot may remain stale. The author already recognizes child and cross-scope limitations, which is correct.

**Reviewer-required implementation acceptance condition:** document Read Committed as the initial lock/recount protocol; acquire a stable scope row before a subsequent count statement; cover imports, replacement acceptance, withdrawal/correction, admin and approval updates; hold lock until all accepted-state/audit/job writes commit. Test two genuinely concurrent database connections. A domain rule spanning multiple scopes requires fixed lock ordering across all involved scopes or a correctly designed Serializable protocol. This is an engineering qualification, not a measured failure.

**Source reason:** [Explicit Locking §13.3.2](https://www.postgresql.org/docs/18/explicit-locking.html) limits row conflicts to the same row; [Transaction Isolation §13.2.1](https://www.postgresql.org/docs/18/transaction-iso.html) explains statement snapshots; §13.2.3 requires handling serialization failures. Locks are also released on rollback to the savepoint under which acquired, so recovery must not continue as if locks remain.

### 2. Tenant context cannot survive every kind of transaction recovery

**Challenge:** FIRST-2 correctly says reapply per new transaction, but savepoint rollback is another boundary. If local tenant setup occurs after a savepoint, rolling back to it removes that setup. Database pool return alone is not the entire proof of tenant isolation.

**Resolution recommendation:** set tenant context at use-case transaction entry before tenant reads/writes. Abort the use case on tenant-context loss or deliberately reinstall it from trusted server state. Test committed and rolled-back tenant A → tenant B → missing-context sequences on a reused connection, plus earlier-savepoint rollback. Ensure the missing/empty setting denies access. This does not make a custom setting resistant to arbitrary SQL from a compromised application; the original brief already states that limit.

### 3. UGC permission cannot be generalized to every target programme

**Challenge:** “Multiple enrolment is legal” would overstate the original source. University mechanisms, provider recognition, programme modes/timing and professional-council rules remain relevant. The 2025 letter’s historical-validity amendment is conditional, rather than retroactive approval of all prior overlaps.

**Resolution:** FIRST-4 is appropriately qualified as written. Retain potentially incompatible overlap as a review case, not fraud or a universal rejection. Require programme-specific authority evidence before giving a final compatibility verdict. No basis found to overturn the author’s recommendation against a global unique APAAR constraint on all enrolment history.

## Associated architecture claims

- The modular monolith, synchronous initial SQLAlchemy usage, PostgreSQL queue and backend-first scope are **decisions**, not conclusions established by the cited specifications. Reasonable for the stated solo-project constraint, but no empirical sufficiency or “fully optimized” claim is supported.
- No supplied implementation demonstrates RLS correctness, concurrency safety, queue recovery, verifiable receipts or throughput. Tests listed in the brief are proposed acceptance tests. An architecture document must retain that future-tense distinction.
- Pinned input/reference snapshots and versioned rules support reproducibility only if retained artifacts actually exist. Hashes alone do not recreate missing data. This is accurately acknowledged by the author.
- A narrow runtime credential plus RLS is useful defence against omitted filters, but all actual disclosure paths and privileged helpers still need review. Author’s statement that RLS does not cover files/logs/exports is an appropriate boundary.
